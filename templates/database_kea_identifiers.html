{{ icon("wrench", "ico-lg") }} Kea reservation identifiers

Finds and repairs reservations whose identifier was stored as text by an older Jen restore or migration. Nothing changes until you press Repair.

What this looks for

Before 5.67.0-beta.11, restoring a Kea backup or import file, or migrating the Kea database, wrote a reservation's identifier as the text of its own hex: the six-byte MAC 34:13:43:e6:0e:2a became the twelve characters 341343e60e2a. The row looks right but Kea never matches the client to it again.

A hw-address of 12, 16 or 40 hex-digit characters, or a DUID whose decoded type is 1 to 4, is offered ticked. A client-id is different: some embedded clients really do send their MAC as ASCII text, so a client-id is offered ticked only when a lease shows the client using the decoded bytes; with no lease to say, it is listed unticked as ambiguous, and when a lease shows the client sending exactly the text it is left alone. Circuit-id and flex-id are never flagged — ASCII hex is legitimate there. Per-host option values of a few fixed-width codes (addresses, masks, times) are listed separately, unticked, for you to review; text options are never listed because their text may be anything. Only rows you tick change, only the identifier or option value, and only if it still holds exactly what is shown.
