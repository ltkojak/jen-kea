# Upgrading from 5.70.0

Everything below changed since v5.70.0 — the last stable release before
this one — that you'd actually notice or need to know about when you
upgrade. Run `sudo ./install.sh` on the new tarball (or use the in-app
updater) the normal way; nothing here needs a manual step beyond what's
called out explicitly. See `docs/runbooks.md` for step-by-step
procedures, and `CHANGELOG.md` if you want the full detail behind any
item below. The previous page, covering everything since 5.69.0 through
the 5.70.0 baseline, is archived at
[`docs/release-history/upgrading-5.69.0-to-5.70.0.md`](release-history/upgrading-5.69.0-to-5.70.0.md).

## Changes can go over Kea's own API; no existing server changes by itself

One step (7.0.0-beta.1). There is no Jen 6: the number is 7 because this release changes what Jen needs on a Kea host (a change can reach a server through the daemon's own API instead of an SSH file replacement), and 6 was skipped on purpose. **No existing server gains a write path on upgrade; switch a server to Live API from its card** (Settings → Kea → *Write mode*). It adds no migration and needs no manual step: the upgrade writes nothing to your configuration, a server that wrote over SSH before still does, and a server that was only read (no SSH host) is still only read.

**What you will see.** The Servers page shows one word per server beside its role: `Live API`, `File over SSH` or `Read-only` (with *, unauthenticated* and *, blocked* where they apply). A server with an SSH host and no setting reads File over SSH; one with no SSH host reads Read-only. Settings → Kea has a *Write mode* card per server with a readiness check, the switch and, where SSH is set up, **Allow the daemon to write its file** and **Take the write right back**. Config history labels three new kinds of row (`rollback`, `switch` and `pending`). The Doctor names a transport value that is not spelled exactly `api`, `file` or `off` (a mistake reads as `off`).

**A server added after the upgrade starts on Live API** and writes nothing until you have run the readiness check on its card, read the facts it shows and allowed changes over the API. The check shows how the endpoint is authenticated (a password, Jen's client certificate, or nothing) and whether it is reached over TLS; where SSH is set up, whether the daemon's account may write its file, whether the file carries an include and whether the file and the daemon agree.

**What changes when you switch a server to the API.** Kea writes its file in its own form: comments and key order are not kept (a 1,932-byte file became 4,769), and the switch is the one moment they are lost. A change is live at once with no restart, guarded by the daemon's configuration digest. Kea writes the file in place, so a crash in the middle of a write leaves a file the daemon cannot start on; where there is no SSH you repair it by hand from Config history. A refused `config-write` is undone by Jen, remembered on the card and blocks further changes to that server until you fix it. One Jen instance per daemon is the supported configuration: inside the two round trips of a change, a second client's `config-set` is overwritten without a trace.

**The Kea host helper has a new build (19, and 20 from 7.0.0-beta.2).** Build 19 adds the three ops behind the card's grant buttons, keeps verifying after a restore of investigation logging, and never makes a backup group-writable. Press **Update helper** on a host only if you want the grant; the legacy `python3` path has no engine for these ops. **Build 20 fixes a race in build 19's re-verify** (see 7.0.0-beta.2 below): press **Update helper** on any host that uses investigation logging.

## 7.0.0-beta.12: a channel's secret is write-only and kept only for the same server, a restricted admin sees only their channels, every bounded number has one table, and a permanent lockout is permanent

Nothing to do on the upgrade: one automatic migration (39, a new `login_lockouts` table; no row of any other table is touched), no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. **Three things you may notice.** Settings → Alerts no longer shows a channel's bot token, SMTP password, webhook URL or API token: the edit form shows *Saved - leave blank to keep* for them, a blank keeps the stored value while the channel delivers to the same place, and a blank after you changed the SMTP server, port or STARTTLS setting (or a webhook's or ntfy server's address) is refused until you type the secret again - the stored one is never carried to the new place. A subnet-restricted admin now sees only the channels scoped inside their subnets and gets "Channel not found." for any action on another; a channel for every subnet prints "Subnet-specific alerts for all subnets" on its card, which is how to find one a restricted admin saved before 7.0.0-beta.11. And a lockout of 0 (until cleared) now counts the failed attempts of the last week instead of the last 24 hours. What else changes: the Security page's attempts and lockout fields accept the bounds the server does (1000; 10080), and the Security and System pages print the number the server applies for a stored value past a bound; a retention of 0 on a history table keeps one day instead of emptying the table; an SMTP port is checked when typed; an OIDC subnet map with a segment that has no colon is refused on save, and a map already stored with one scopes an unmatched login to no subnets rather than every subnet under `subnet_map_default = all`; an OIDC login that changes an account's role or subnets refreshes that account's other open sessions; a permanent lockout is reported as one at any configured duration (a 999-minute lockout used to read as permanent); the support bundle masks `secrets`, `tokens`, `api_keys` and `password2`; and a rollback over the API that the daemon answered with an empty configuration says so instead of blaming the file. **From the first independent review of the 7.0 line (beta.11):** a lockout of 0 ("until cleared") is really until cleared now - it used to end by itself within a day because the failed attempts were pruned - and the upgrade adds the small table that records it (migration 39, automatic); the minutes a locked-out user is told are the minutes until the lockout really ends, not the oldest attempt's; the rate-limit, session, alert and report settings are saved in one transaction and the page says "could not be saved" when they were not, instead of "saved"; and an alert channel whose stored subnet scope is damaged (empty or not a list) receives no subnet-specific alert instead of every subnet's.

## 7.0.0-beta.11: a restricted admin's channel covers its subnets, the lockout mode is part of the strictness, and a stored number is read as it is bounded

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. **Three things you may notice.** A subnet-restricted admin saving an alert channel must select at least one of their subnets ("Select at least one subnet this channel should cover."): the untouched form used to store a channel for every subnet, and it then carried the lease, device and client alerts of subnets its creator cannot see - a channel such an account saved before this release still has that scope until it is edited, so look at Settings → Alerts if restricted admins have saved channels. An admin can no longer move login rate limiting away from *both* (to IP or username alone, or between the two): *both* counts two buckets and locks on the larger, so leaving it is a loosening and a superadmin's change; moving to *both* is still an admin's. And a number stored past the Security page's bounds by an earlier release is read as the bound now (the previous section said such a value kept working - for the audit retention it did not: the daily prune failed on it silently, and prunes at ten years now). What else changes: a group in the OIDC subnet map whose ids are all mistyped scopes the account to no subnets instead of dropping the group (which, with `subnet_map_default = all`, let the account in unrestricted); a stored subnet scope that is not a list is no subnets; a rate-limit mode outside its four words is *both*, not off; under *both*, the minutes remaining are measured in the bucket that locked (a username-triggered lockout used to say "1 minute"); a discard ticked over a file that cannot be read is refused instead of answering "proved (unreadable)"; a rollback over the API refused before its set for any reason reads "still have the NEW config" and names no settlement; the support bundle keeps a `[DEFAULT]` section as itself and masks `DBPassword`, `pass_phrase` and `credential`; and this page's two earlier sections name the readiness check as the card does.

## 7.0.0-beta.10: a rollback is refused before its set, a scoped admin reads no log, and an admin tightens only

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. **Two things you may notice.** A subnet-restricted admin who opens Settings → Logs is sent back to Servers ("Logs need access to all subnets."): the audit and alert-delivery rows carry no subnet, and their text names what such an account cannot see - give the account every subnet, or read the log as a superadmin. And an admin can no longer turn the session timeout or login rate limiting off, lengthen the timeout, allow more login attempts or shorten the lockout: those are a superadmin's changes now, as the MFA policy has been since v5.69.0 (an admin may still tighten any of them). The Security page bounds its numbers (attempts up to 1000, lockout up to a week, audit retention up to ten years) - a value beyond them is refused with the bound named, and a value already stored beyond them keeps working until it is changed. What else changes: a rollback over the API whose file cannot be proved is refused before anything is sent (the daemon and its file both keep the change; Config history is the way back) instead of leaving the daemon rolled back and the file not; a pending change whose age the database measures as negative (its clock stepped back) is settled on the next ask instead of reading "in progress"; a lockout check that cannot reach its table refuses the login for a minute instead of allowing it; a form value with a digit that is not an ASCII digit is refused instead of raising; the support bundle masks a list or a dict under a secret-named key and a spaced key such as `Client Secret`; and the sentences that send you to the readiness check name it as the card does ("press Run check under Readiness check").

## 7.0.0-beta.9: a pending change is aged by the database's clock, and a rollback puts the file back too

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. **One thing you will see on a Live API server with an SSH host: its card asks for the readiness check once more** - the stored result is now bound to the SSH user and the config path as well as the API address and the SSH host, and a result from an earlier release is checked again (press *Run check* under *Readiness check*, then tick the boxes step 3 asks for). What changes: a change left half-done is aged by the database's own clock, so a database host whose clock is ahead of Jen's no longer makes it read "in progress" until the skew has passed; the rollback of a change over the API writes the file back as well as the daemon when the file carries the change it undoes, and the sentence for a record with no planned file names the box beside *Settle it now* before the restart; the support bundle masks a string under a secret-named key in every member and is downloaded by the page's button, not by a link; and the refusals of the Write mode card name its boxes by the labels it prints.

## 7.0.0-beta.8: a secret is masked by name alone, and every member of the bundle goes through one pass

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. What changes: the support bundle masks a secret by the name of its key and never by its value (**a bundle made by an earlier release on a box whose `api_pass`, database password or any token begins with `/` or a drive letter carries that secret in `config.ini.redacted`: treat such a file as a secret** - this is in 5.70.0 as well), and the notes in its `README.txt` are scrubbed and cut; *Run check* under *Readiness check* on the Write mode card asks for your password again like the card's other buttons and leaves an audit row; the box beside *Settle it now* works for a change recorded before 7.0.0-beta.5; a readiness result dated in the future closes the gate until the check is run again; and one change over the API re-reads the host's facts once, not twice.

## 7.0.0-beta.7: an address leaves the box without its password, and the write gate is a read

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 22 still), and no server changes its write mode. What changes: a support bundle never carries the user name or password of an address (if a saved `api_url` still has one inside it, Health's "Every endpoint has a credential" row names it - move it to the user and password fields; **a bundle downloaded from an earlier release on such a box carries that password, so treat it as a secret**); a page no longer reaches out to a Kea host to print the Live API badge; and the alert for a change left half-done carries a box beside *Settle it now* that keeps the change when the file was edited by hand afterward.

**7.0.0-beta.6** is 7.0.0-beta.5's product: 7.0.0-beta.5 was tagged and never released (its release run failed on a leak between two tests of the suite). Everything under 7.0.0-beta.5 below applies to it unchanged.

## 7.0.0-beta.5: the file is proved by the daemon's own clock

One migration (38, additive: one nullable column on the config history), no new setting and no sudoers line; **press Update helper (build 22) on every Kea host that has an SSH host and a server on Live API** - without it a Live API server accepts a write only over a file Jen itself rendered (or the one a change was planned over), and the card says "press Update helper". Nothing else to do on the upgrade, and no server changes its write mode. What changes: before a change over the API replaces the file on the Kea host, Jen no longer compares the file with the daemon's configuration through a table of what Kea writes out by itself - that table kept finding one more thing it did not know, and beta.4's review found a deleted subnet `valid-lifetime` read as agreement. It asks the host and the daemon instead: was the file written before the daemon last loaded a configuration (the host's own clock; `jen-kea-helper` build 22 reads the file's modification time and the daemon's `status-get`), is it Jen's own rendering of what the daemon runs, or is it the file the change was planned over? A hand-authored file that omits what Kea writes out (a `code`, a `space`, an inherited `valid-lifetime`) and that the daemon loaded is accepted; an edit nobody loaded is refused with both times in the sentence, and the way out is the one the sentence names: restart Kea there (or reload its configuration), or discard the edit from the card. The card's *Config file matches running config* row says what was proved in the same words. A change's record now carries the file the change was planned over, so *Settle it now* writes only over that file; a record an earlier release left (it carries none) is refused with "restart Kea there to load the file as it stands, then Settle it now". A restore over a change that is live and whose file write is owed asks for the settlement first; the file branch of a restore now takes the same lock as the API branch; a change that is live and not yet in its file reads "live in the daemon on <host>, not yet in its file", never "failed". A switch records the readiness facts its own write made (the file is the daemon's rendering afterward) and a consent the switch used up is not left on record; leaving Live API clears a remembered refusal; a switch over an unsettled change is refused. The card offers the discard box to a server only when a readiness result is on record, and a tick that arrives with none names the check. The import names the server it goes to - the first that takes changes - and says "restart it" only for File over SSH. Health has a row, *Live API changes are open*; the Doctor names two server sections that point at one Kea endpoint; a support bundle's `servers.json` says whether the gate is closed and why, with the proof's times.

## 7.0.0-beta.4: a settlement asks the file before it writes it

Nothing to do on the upgrade: no migration, no new setting, no sudoers line and no helper build (the helper is build 21 still), and no server changes its write mode. What changes: a `config-write` - the one that finishes a change a crash left half-done, the one a change over the API sends, the one a switch to Live API sends - now reads the file on the Kea host first (an edit it finds is a row in Config history) and refuses to overwrite one the daemon never loaded. The card says so above **Settle it now** ("a change of ... is live and its file write waits: the file on kea-a carries an edit the daemon has not loaded (at Dhcp4.user-context)") and the ways out are the ones the sentence names: restart Kea on that host, or discard the edit from the card (it stays in Config history). A change whose record cannot be written is not sent, and one whose record cannot be finished is not reported as done. A consent is recorded only for what the facts called for, so a box in a hidden panel can no longer ride along, and a stored result that names no endpoint is checked again. The gate's own sentences (the daemon's account, a file's mode, an include's path) are a superadmin's, in the line a change flashes as well; an admin or a viewer reads the mode and that a change will stop until a superadmin has read the card. The Servers page names every server's write mode for a fleet of one, two or three, a support bundle's `servers.json` carries the write mode and the readiness facts, and an import reads from the first server that takes changes. A scalar deleted from the config file while the daemon runs another value than Kea's default is a difference now, not agreement.

## 7.0.0-beta.3: Write mode is one choice, and the card says where and why

A mode is a choice with its steps under it. Nothing to do on the upgrade: no migration, no new setting, no server changes its write mode, and the config value (`config_transport = api | file | off`) is unchanged. What you will see: Settings → Kea → *Write mode* is one block per server - three radios (Live API, File over SSH, Read-only) with the current one marked, the steps the selected mode needs under it with their state and their own buttons, one set of boxes for what you accept, and the switch button at the bottom, which says what is holding it; the Servers page badge and the Doctor use the same words and the badge links to the card. The switch is now the one consent act (the readiness check only reads), given for the facts you read and needing a recent confirmation of your password. The card names its cause: a helper below build 19 is not "no SSH", and a file that does not match the running config says **where** ("at Dhcp4.subnet4[2]…: the file says …, the daemon …"; a secret's value is never printed). A file with a key *deleted* from it is a difference now, not only an added one, and every preview validates on the server's own write mode (a Live API server with no SSH previews). **A server consented to in beta.1 or beta.2 without a record of which consents were given counts as having accepted the file rewrite only**: an endpoint that lost its authentication, or a file that no longer matches, blocks until you tick step 3 again. Viewers no longer see that an endpoint has no authentication. **Press Update helper (build 21) on a Kea host that uses investigation logging or Live API**: build 21 refuses a config path or state-file name that ends in a newline (the basename wall is a full match now); nothing depends on it to work. A server that is already in Live API records a consent from its card (the button reads *Record consent* while the gate is closed).

## 7.0.0-beta.2: a logging race fixed, and the register of the first beta's review

No migration, no new setting, nothing to do on the upgrade itself, and no server gains a write path. **Press Update helper (build 20) on every Kea host that uses investigation logging**: with build 19 a turn-on whose arm landed just after the host's timer ticked inside the finished session's window could be put back by the host, so logging went on and then silently off while the host showed armed; build 20 acts only on the marker of the session its record is of. What else you will notice: allowing changes over the API is now an act - the card's control appears once the facts are on the page, asks for each consent the facts call for and a recent confirmation of your password, and Jen re-reads the facts hourly (and before a change when they are a day old) without asking again, closing the gate with the fact's own sentence only when something the consent does not cover appears; the badge says `blocked` where the gate does (for an admin the sentence; a viewer sees a neutral phrase); a page never settles a half-finished change - **Settle it now** on the card does, and an unreadable record of changes stops them with a sentence; a mixed change inside the host's restore window stops at Plan and writes nothing; Author Kea Config names a server on the API as not a target; a server consented to in beta.1 counts as having been given all the consents until you allow again.

**Recovery bundles.** A recovery bundle exported on 5.x restores on 7.0 (the major-version check accepts it). Export a fresh bundle after upgrading.

**What stays on the file path in this beta.** Control-socket changes and investigation logging (the host restores the marker from the file), the first file Author Kea Config writes, dhcp6 and D2. A restore or an import applied to an API server goes over the API with no restart.
